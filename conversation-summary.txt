DSH Superagent 对话摘要
========================

记录时间：2026-11-18 14:11–15:03（Asia/Shanghai）
对话双方：用户与 superagent 调度代理（本部署）
对话主题：路由层与工作层的分工、模型与配置位置、现有规则与触发条件
说明：本文件即该对话被受理后的交付物，由工作层（执行代理）整理，不改动仓库既有文件。


一、仓库与工作线路
------------------
- 本部署负责的仓库：n-loml/dsh-superagent-test（Feishu 与 GitHub 两个来源）。
- 工作线路：用户在飞书提需求 → 路由层（orchestrator）判断范围并建任务单
  → 工作层（executor）在独立工作目录中调查、实现、跑检查与评审、提 PR
  → 路由层回到原线程给出可查看的 PR 链接与结果。
- 纯提问由路由层直接回答，不建任务单、不改代码。
- 需要 DSH 进程与账号登录保持在线：离线期间收不到飞书消息，也无法驱动执行
  层和推送代码；任务执行同样在这台机器上。


二、路由层与工作层的分工
------------------------
- 路由层（router / 评估层，orchestrator）：读取消息、判断归属、生成候选、
  做评估、决定建单或忽略，并把结果回执到原线程；也负责按规则观察和线程跟进。
- 工作层（worker / 执行层，executor）：在隔离的工作目录内完成实现、运行检查
  和自评审、提交并推送 PR；不在原对话里做调度判断。
- 相较常规 agent 的优势：调度判断与实现分离；执行在隔离目录内完成并可验收；
  能按启用的规则主动巡检、按线程持续跟进。


三、模型选择
------------
- 对话中确认：本部署的路由层（eval）与工作层（executor）两个角色此前都未
  单独指定模型，均跟随 DSH 默认模型 deepseek-flash，两处实际是同一个默认。
- 框架支持为两个角色分别设置模型项（服务商、模型、推理强度），留空即继承
  DSH 默认；把两项设成不同模型即可让两层使用不同模型。
- 对话后段用户又在面板中保存过一次 eval 配置（含 eval.mode 与 eval.model），
  该次具体取值未在对话中记录。
- 不按单条消息切换模型或推理强度；推理强度与上下文上限由 agent 框架的模型
  配置决定，只有重试等情况才会在内部记录中体现。
- “按任务难度自动升级模型”在当前配置中不存在。


四、配置位置
------------
- 统一在 DSH Web 面板（http://127.0.0.1:3082）的设置中分块修改，保存后生效：
  * 评估（eval）：评估模式（observe / auto）、评估超时、router 模型项。
  * 执行（executor）：worker 模型项（服务商 / 模型 / 推理强度）、并行工单数、
    prepare 命令。
  * 策略（policy）：接受模式、启用的规则、允许来源。
  * 来源（source:feishu / source:github）：监听范围与开关；Feishu 群可把监听
    从“仅 @ 提及”改为“全部消息”。
  * 模型（models）：模型 provider 配置。
- 两层的模型字段是同一套：服务商、模型、推理强度，留空表示继承默认。


五、现有规则与触发条件
----------------------
- 触发：默认群内需要 @ 机器人才会作为输入；改为“全部消息”监听后，群内所有
  消息都会进入评估。私聊可直接发，无需 @。进程必须在线，离线期间的消息不会
  实时进入，也不会自动回捞，需要人工要求时再读群历史。
- 评估发生的位置：不在收消息那一步，而在“评估”步骤：
  消息被收录（监听 + 允许来源）→ 生成候选 → 路由层读该线程窗口 → 判断三件事：
  讨论针对本项目、参与者有明确改动意图、方向已足够确定且是小范围本地改动
  → 记录决策 → auto 模式命中规则就建单并回执，不命中就忽略且不打扰。
- 显式请求（点名要求做的事）不经过规则过滤，直接走派单；规则只用于筛选主动
  观察到的候选，且不能扩大范围。
- 当时启用的规则：
  * copy 文案修正：明确的错别字、措辞、标点或既有翻译纠错，须保持产品承诺与
    业务含义不变。
  * visual 视觉修正：明确的局部间距、对齐、溢出或样式修复，且已有指定目标或
    客观既有标准可还原；“不一致 / 不好看 / 难理解”不构成目标，不重设计、
    不加交互、不改行为。
- 模式含义：observe 只记录判断不派工；auto 命中规则即建单。
- 演变：最初“写一份对话摘要 txt”不落在 copy / visual 两条规则内，评估结论为
  忽略；用户追问后确认新增文件属于新增内容而非纠错或视觉修复。随后新增第三条
  规则 write txt（按要求写出文本文件）并把评估模式切到 auto，该请求因此被受理，
  建单并交给工作层执行——本文件即这次执行的产出。


六、关于“这个任务执行不了是受限于哪里”
--------------------------------------
限制不在能力而在授权，分三层：
1. 准入规则：只启用 copy 与 visual，写摘要报告是新增内容，两条都不命中。
2. 工单范围：工单只承接仓库内的小范围内部改动，产出报告类交付物不在其范围。
3. 当前模式：observe 下即使命中规则也只记录判断，不建单派工。
路由层本身没有拒绝执行；执行层写文件、提 PR 的能力完全具备。想看到完整调度
链路，需要一条具体的、仓库内的小改动（或新增 write txt 这类明确规则）。


七、过程中出现的环境问题
------------------------
- 首次建单在工作目录 prepare 阶段克隆仓库失败：TLS 握手报错
  （github.com 被解析到 198.18.0.18 这类代理 fake-ip 地址，代理链路未生效），
  重试多次均失败，工单因此失败，需要先恢复 GitHub 访问。
- 恢复代理 / TUN 后验证：https://github.com 返回 200、gh api user 返回账号、
  git ls-remote 能列出 refs；用户明确要求“重试”后重新派工，任务得以继续。
- 失败工单不会自动重启，需要用户明确要求重试。


八、结论
--------
路由层负责“判断该不该做、范围是什么、结果怎么回”；工作层负责“在隔离目录里
把具体的事做完并交付 PR”。模型、评估模式、规则、来源监听等都在 DSH Web 面板
的设置中分块调整。主动受理依赖规则命中与 auto 模式；规则只约束主动观察到的
候选，不限制明确的显式请求。本摘要文件即 write txt 规则启用后的一次完整调度
产出。
